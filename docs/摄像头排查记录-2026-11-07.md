# 摄像头“没图 / 图不满 / 一直跳”排查记录

- 日期：2026-11-07
- 涉及固件：FW=2158（坏）→ FW=2166（修好）
- 结论一句话：**图像链路和硬件都没坏，是固件里的采集配置跑偏了**；恢复成 GitHub `origin/main` 上那版配置后立刻正常。

---

## 1. 现象

| 现象 | 实际含义 |
|---|---|
| 上位机“已连接”、遥测正常，图像区全黑 | DCMI/DMA 一个字节都没往内存搬 |
| 只看得到画面上 1/4，下面全黑 | 采集模式与传感器输出宽度不一致（只有帧的一部分进缓冲） |
| 整屏斜纹、条纹 | **行宽错配**：把 752 字节的行当成 188 字节来切（一条真行被切成 4 条假行） |
| 画面每 0.8 秒明显抖一下 | 极性“自动搜索”在反复重写 `DCMI->CR`，把正在跑的帧打断 |

---

## 2. 根因（三条，按危害排序）

### 2.1 A/B 测试用的配置没撤（主因）

FW=2152 为了验证“传感器还能不能出图”，把 bin4 临时退回全分辨率：

```c
/* 2152 留下的（坏） */
cam_sccb_write_reg(0x0D, 0x0300);   /* 不做 bin ⇒ 752×480 */
cam_sccb_write_reg(0x0B, 300);      /* 快门 300 */
cam_sccb_write_reg(0xAD, 300);      /* AEC 上限 300 */
```
```c
/* app.c 同时把采集模式切回了 752 */
board_cam_set_mode(0);
```

测试完之后只改回了一半，于是出现两种错配：

- 传感器 188 宽 + 固件按 752 切行 ⇒ **斜纹**
- 传感器 752 宽 + 固件按 188 切行 ⇒ 只采到 1/4 帧，窗口还在环形缓冲里滑动 ⇒ **“站不满 + 一直跳”**

### 2.2 极性“自动搜索”其实永远不会锁定

```c
#define CAM_POL_ROTATE  1   /* 开轮换 */
#define CAM_POL_MODE    0   /* 0 = 普查 */
```

而锁定分支被条件编译掉了：

```c
#if (CAM_POL_MODE != 0)      /* MODE=0 时这段根本不存在 */
    if ((step >= CAM_POL_MIN_STEPS) && (dbg_pol_idx == CAM_POL_STORE)) { done = 1; }
#endif
```

⇒ 每 800ms 无条件重写一次 `DCMI->CR`。而 **DCMI 在运行中改 PCKPOL/HSPOL/VSPOL 不会重新同步**（本文件早期注释里已有这条结论），正在跑的帧会被打断 ⇒ 画面周期性抖动。

### 2.3 为了“修图”往传感器写的寄存器（最危险）

FW=2140~2155 期间，为了救图陆续加了这些“修复”动作：

- `0x0C` 复位脉冲（先写 1 再写 0）
- `0xAF = 0x0003`
- 14 条寄存器“整表回写出厂值”
- `0x0D = 0x0300`

其中整表里把**保留寄存器**写成了自己猜的值：

| 寄存器 | 我写的（错） | 手册 Table 8 默认值 |
|---|---|---|
| `0x20` | `0x0007` | **`0x01C1`** |
| `0x24` | `0x0002` | **`0x0010`** |

手册开头明确警告：*"Writing and changing the value of a reserved register (word or bit) puts the device in an unknown state and may damage the device."*
FW=2158 按真实默认值写回后，图才回来。**这是“动了寄存器就没图”的确切来源。**

## 3. 正确配置（= GitHub `origin/main` 那版）

| 项目 | 正确值 | 说明 |
|---|---|---|
| `R0x0D` Read Mode | 读-改-写：`(v & ~0x0F) | 0x0A` | `[3:2]=2` 列 bin4、`[1:0]=2` 行 bin4 ⇒ **188×120** |
| `R0x0B` 快门 | `≤ 110`（默认 100） | 行 bin4 后一帧只有 120 行，曝光 ≥120 时**永远完不成一帧** |
| `DCMI->CR` | `0x4021` | ENABLE + CAPTURE + PCKPOL，即**极性组 1** |
| 采集模式 | `board_cam_set_mode(1)` | `cam_row_bytes=188 / cam_span=120 / cam_dcol=1` |
| DMA | 连续 + 循环，`22560` 个字（90240B） | 一帧 188×120 = 22560B，缓冲装 4 帧 |

极性组号的位映射（`board_cam_apply_polarity`）：

```
bit0 = PCKPOL   bit1 = HSPOL   bit2 = VSPOL
组 1 = PCKPOL=1, HSPOL=0, VSPOL=0  ⇒  CR = 0x4021   ← 这台车唯一能出图的组合
```

> 注意：极性**不能靠猜**。同样一份 CR，752 模式能搬数据、188 模式却一字节不动；
> 组 0 / 组 3 / 组 6 在 188 模式下都表现为“有行中断、没有数据”。唯一可行的是组 1。

## 4. 怎么验证（不用猜，看心跳）

上位机 `tools/car_ui.py` 会把收到的每一行写进 `tools/log_*.txt`，直接看 `S `. 开头那行：

| 字段 | 含义 | 正常值（188 模式） |
|---|---|---|
| `MD` | 采集模式 | `1` |
| `BIN` | bin4 是否写成功且回读一致 | `1` |
| `R0D` | `R0x0D` 回读 | `030A` |
| `P` | 当前极性组 | `1` |
| `CR` | `DCMI->CR` | `00004021` |
| `W` | DMA 当前写入行号 | **一直在跳** |
| `ND` | DMA 剩余传输字 | **一直在变** |
| `FL` | 实测一帧行数 | `120` |
| `K` | PA6 上实测 PCLK（kHz） | 188 模式 ≈ 4300~5000；752 模式 ≈ 20000 |

**判据**：`MD=1 && BIN=1 && R0D=030A && W 在跳` ⇒ 图一定在。

## 5. 以后别再犯（血泪规则）

1. **A/B 测试用的配置不许留在固件里。**
   要么当次改回来，要么写成编译开关、默认关闭，并在注释里标“临时”。
2. **不许给保留寄存器写非默认值。**
   要“恢复出厂”只能照手册 Table 8 逐条抄，抄完再回读核对，不明白的寄存器**不要写**。
3. **DCMI 极性只允许固定一组。**
   运行中改 `CR` 的极性位不会重新同步；必须 `Stop → 改极性 → Start`。
4. **出问题先 diff，不要重写。**
   第一步永远是 `git diff <能跑的那个提交> HEAD -- <相关文件>`，先看差了什么，再动手。
5. **测“有没有数据”要用累积计数，不能用差值。**
   `DMA->NDTR` 在循环模式下会绕圈，`装载值 - NDTR` 在多圈时给出的是随机小数
   —— 本次就用它误判过“188 模式一个字节都不搬”，从而导致自动回退 752、画出斜纹。
6. **少加临时诊断。**
   每加一处就多一个可能改变时序的因素；诊断一律走命令触发，不要塞进主循环。

| 固件 | 做了什么 | 结果 |
